Отчёт обучающегося по практике (основная часть и заключение)

Объём при оформлении по ГОСТ 7.32-2017: ориентир 5–7 страниц. Ниже текст для переноса в документ.


ОСНОВНАЯ ЧАСТЬ

1 Изучение материалов по индивидуальному заданию и технологиям реализации проекта

В рамках первого этапа практики студентом была выполнена самостоятельная подготовительная работа, не связанная с прохождением отдельного дистанционного курса, а направленная на углублённое изучение кейса «Сервис для сокращения URL-адресов и генерации QR-кодов» и технологий, необходимых для реализации серверной части сервиса в соответствии с методическими материалами и планом спринтов. Целью этапа являлось формирование достаточной теоретической базы для осознанного выбора архитектурных решений и последующей разработки безпрерывного сценария «создание короткой ссылки — сохранение в базе — редирект по коду».

В ходе подготовки студент последовательно проанализировал формулировку кейса и требования первых этапов: определены ключевые пользовательские сценарии, ограничения MVP, перспектива развития (авторизация, статистика переходов, генерация QR-кодов). Отдельное внимание уделено принципам проектирования REST API: выбору ресурсов и путей, кодам ответов HTTP, формату ошибок в теле ответа, валидации входных данных. Были изучены типовые подходы к генерации коротких идентификаторов (в том числе случайные строки в алфавите base62 и детерминированное кодирование числового идентификатора записи), а также вопросы уникальности кода на уровне базы данных и обработки коллизий.

Параллельно прорабатывались материалы по языку программирования Go и экосистеме разработки сетевых сервисов: организация модулей, работа с контекстом, обработка ошибок и их оборачивание для сохранения причинно-следственной цепочки, базовые практики структурирования проекта (разделение точки входа, конфигурации, транспортного слоя и бизнес-логики). Изучена документация веб-фреймворка Gin с акцентом на маршрутизацию, привязку параметров пути, работу с JSON и порядком регистрации маршрутов во избежание конфликтов с укороченными URL.

Для части, связанной с хранением данных, студентом освоены основы проектирования реляционной схемы под PostgreSQL: нормализация минимально необходимой модели на этапе MVP (таблица ссылок), ограничение уникальности на поле кода, использование миграций для версионирования схемы. Были рассмотрены драйвер pgx, пул соединений и типовые ошибки при выполнении запросов. Изучены инструмент миграций goose и подход к конфигурированию через переменные окружения без включения секретов в репозиторий.

Важным элементом подготовки стало знакомство с контейнеризацией для локальной разработки: составление описания сервиса базы данных в Docker Compose, согласование портов и параметров подключения с приложением. Дополнительно проработаны вопросы структурированного логирования (библиотека zap), уровней логов и разграничения диагностической информации для HTTP-слоя и прикладной логики.

Итогом первого этапа стала сформированная база знаний, достаточная для перехода к практической реализации backend-ядра сервиса сокращения ссылок в рамках индивидуального задания.

2 Разработка проекта «Сервис для сокращения URL-адресов и генерации QR-кодов» (backend, этапы 1–2)

В рамках второго этапа практики студент приступил к реализации серверной части сервиса в соответствии с кейсом: обеспечение создания короткой ссылки по длинному URL, сохранение соответствия в базе данных и редиректа по переданному в пути параметру кода. Функциональность генерации QR-кодов, личного кабинета и учёта переходов на данных этапах заложена в архитектуру и схему данных, но отнесена к последующим итерациям, что соответствует поэтапному плану работ.

На подготовительной стадии был проведён анализ и обоснованный выбор стека: в качестве языка реализации выбран Go; для HTTP API — фреймворк Gin; в качестве СУБД — PostgreSQL с использованием драйвера pgx; для миграций — goose; для логирования — zap. Решения зафиксированы в проектной документации с указанием компромиссов (например, удобство знакомого фреймворка и скорость разработки MVP при сохранении слоистой архитектуры).

Спроектирован REST API для текущего объёма работ: метод проверки работоспособности GET /health, создание короткой ссылки POST /shorten с телом запроса в формате JSON и полем исходного URL, переход по короткой ссылке GET с подстановкой кода в пути с ответом-редиректом на исходный адрес. Описаны форматы успешных и ошибочных ответов, применяемые коды состояния HTTP, правила валидации URL (абсолютный адрес, схемы http/https) и формата кода.

Разработана модель данных: таблица links с суррогатным ключом, уникальным текстовым кодом, исходным URL и меткой времени создания; подготовлена SQL-миграция с индексами, необходимыми для типовых запросов. Отдельно концептуально описано расширение схемы под пользователей и журнал посещений для будущих спринтов.

Реализована слоистая архитектура приложения: HTTP-обработчики (handlers) отвечают за транспортный уровень и преобразование ошибок в единый JSON-формат для клиента; слой сервиса содержит валидацию, генерацию короткого кода и сценарии повторных попыток при коллизии уникальности; слой хранения инкапсулирует запросы к PostgreSQL и переводит ошибки СУБД в доменные. Общие сущности и коды ошибок вынесены в пакет доменной модели.

Настроено окружение разработки: репозиторий с модулем Go, файл описания сервиса PostgreSQL в Docker Compose, примеры файлов переменных окружения для приложения и для goose, инструкция по запуску с нуля в README. Конфигурация приложения считывается из переменных окружения; строка подключения к базе может собираться из отдельных параметров или задаваться целиком. Реализовано структурированное логирование с разделением уровней: стандартные журналы HTTP-запросов фреймворка сохранены, дополнительно используются отладочные и ошибочные записи в критических точках обработки без дублирования одной и той же ошибки на нескольких уровнях.

Функциональные требования текущего этапа проверены по сценарию: поднятие базы, применение миграций, запуск сервера, создание короткой ссылки запросом к API, переход по выданному адресу с ожидаемым редиректом. Таким образом, сформировано работающее ядро сервиса, готовое к демонстрации и дальнейшему наращиванию функций в соответствии с кейсом.


ЗАКЛЮЧЕНИЕ

В ходе прохождения практики было выполнено два взаимосвязанных направления работы.

Во-первых, проведена самостоятельная подготовка по индивидуальному заданию и стеку технологий: изучены постановка кейса сокращения URL и перспективы развития сервиса, принципы проектирования REST API и хранения данных, особенности разработки на Go и использования Gin, PostgreSQL, миграций, контейнеризации и структурированного логирования.

Во-вторых, выполнена практическая разработка backend-части проекта «Сервис для сокращения URL-адресов и генерации QR-кодов» в объёме первых этапов: выбран и обоснован стек, спроектированы API и схема базы данных, реализованы сохранение и выдача коротких ссылок, редирект по коду, обработка типовых ошибок, миграции и документация по запуску.

Совокупность выполненных работ демонстрирует освоение практических компетенций в области разработки сетевых приложений и работы с реляционными базами данных, а также способность поэтапно реализовывать функциональность в соответствии с методическим заданием. Сформированная основа позволяет на следующих этапах практики или учебной деятельности подключить интерфейс пользователя, авторизацию, генерацию QR-кодов и учёт переходов без смены базовых архитектурных решений.

ФИО, группа, место практики, даты вносятся по приказу и титульному листу отчёта.
